# 通用快捷填写验证原型

当前手动重试版新增 [悬浮入口与 5 秒延时填写](floating-retry.md)。仅通过编译与静态检查，未自动执行输入验证；蓝屏根因仍未解决。

用户已选择“手动定位 + 搜索账号 + 快捷填写”的第一版路线。逐应用识别、浏览器扩展和自动保存凭据作为后续增强，不再作为第一版的前置条件。

本原型用 Rust 和 Win32 创建临时测试面板；它不是正式 UI，后续仍采用 Tauri 2 + React。当前只有一条硬编码的 QQ 演示记录，不支持保存、导入或使用真实凭据。

## 运行

```powershell
pwsh -NoProfile -File scripts/Start-QuickFillDemo.ps1
```

1. 在目标应用中点击一个空输入框。
2. 按 `Ctrl + Alt + Space` 呼出面板，搜索 `QQ`。
3. 选择“填用户名”或“填密码”；面板收起后在原光标处输入。
4. 连续填写需要先定位账号框，选择“用户名 → Tab → 密码”。仅当一次 Tab 确实进入密码框时使用。

用户名为 `10000000`，密码为 `Demo-验证-🔑-482!`，均为虚构测试值。不要提交登录；原型不发送 Enter，也不点击登录按钮。输入会插入光标处或替换用户当前选中的文本，不主动清空输入框。

Esc 或“收起”隐藏面板，快捷键可再次呼出。切换到其他窗口取消当前请求，但保留面板和任务栏入口，可从任务栏找回。没有可用输入目标时快捷键仍显示面板，填写按钮禁用并显示提示。退出时点击“退出验证程序”。快捷键被占用时启动失败，不会静默更改其他应用的快捷键。

蓝屏后手动重试期间修复：旧版将目标捕获失败当作隐藏面板条件，且使用无任务栏入口的工具窗口，导致用户无法找回面板。新版将“显示面板”与“允许填写”分开。已完成静态检查与编译，自动运行测试仍保持禁用；更早的自测记录不代表本次变更已运行测试。

## 当前实现

- RegisterHotKey 注册 Ctrl+Alt+Space，不使用全局键盘监听记录输入。
- 呼出前记录原前台 HWND、PID、线程、原生焦点控件及进程句柄，请求有效期 60 秒。
- 搜索仅查找原型自己的固定记录，不读取目标应用的任何输入内容。
- 等待 Ctrl、Alt、Shift、Win 和鼠标按键释放；确认面板仍在前台、目标仍存活后恢复目标。
- 恢复后验证原生焦点一致，每个 Unicode 字符发送前再检查窗口和焦点。使用 SendInput，不经过剪贴板。
- 中文和 UTF-16 代理对随同虚构密码进行验证。连续填写只发送一次 Tab，之后重新检查焦点所属窗口。
- 失败或部分发送不自动重试。不会为了填写自动提权。

## 验证

```powershell
pwsh -NoProfile -File scripts/Test-WindowsValidation.ps1 -Mode quickfill
```

自测启动本程序自己的原生登录窗口，实际发送全局快捷键，设置面板搜索条件并调用与按钮相同的命令处理路径，最后由测试窗口验证自己的字段。只针对自建窗口发送输入。

验收项：用户名单项填写；含中文和 emoji 的密码单项填写；用户名 + Tab + 密码；无搜索结果不填写；面板失去前台后旧请求不填写。自动测试不等于真实客户端兼容性结论，也不覆盖物理鼠标点击的全部时序。

2026-09-10 实测：上述五项在最终输入时序调整后连续三轮通过，原有 UIA 自测也通过。早期重复测试出现过字段校验偶发失败；增加了测试用例间同步、恢复窗口后 150ms 等待及再次核验，并将字符间隔设为 10ms。三轮通过仅证明当前受控样本的结果，未证明所有焦点竞态已消除。

## 已知边界

- 原生焦点 HWND 不能识别 Chromium 内部的 DOM 输入框变化；本方案依赖用户选择正确位置，不能提供浏览器域名验证或防钓鱼保证。
- Windows 的焦点检查和 SendInput 不是原子操作，用户或其他程序同时切换焦点仍存在竞态；当前只能减少误填风险，不能保证所有情况下零误填。
- 模拟输入被管理员权限、游戏或特殊控件拒绝时会失败。SendInput 返回成功也不能证明目标实际接受了字符；真实应用需人工观察。
- 中文输入法、不同键盘布局、缩放、多显示器与各版本 QQ 尚未完整验证。
- 当前可输入内容只有固定演示值，尚无密码库、锁定、托盘或悬浮球；正式 UI 设计在此交互链路确认后进行。
